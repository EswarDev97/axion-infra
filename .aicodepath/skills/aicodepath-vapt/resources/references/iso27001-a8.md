# ISO 27001:2022 — Annex A.8 Technological Controls Reference

Standard: ISO/IEC 27001:2022
Scope: All systems within the Information Security Management System (ISMS) boundary.
Relevant annex: A.8 Technological Controls (34 controls)

---

## Secure Development Lifecycle Controls (A.8.25 – A.8.32)

These are the primary controls for application security:

| Control | Name | Code-Level Requirement |
|---------|------|----------------------|
| **A.8.25** | Secure development life cycle | Formal SSDLC policy with security gates at: requirements (security stories), design (threat model), implementation (coding standards), verification (SAST/DAST/pentest), deployment (security gates) |
| **A.8.26** | Application security requirements | Security requirements documented and traceable for every feature; security acceptance criteria in Definition of Done |
| **A.8.27** | Secure system architecture and engineering principles | Least privilege, defense-in-depth, fail securely, separation of duties, complete mediation enforced in design |
| **A.8.28** | Secure coding | Written secure coding guidelines addressing OWASP Top 10; mandatory code review with security focus; annual developer security training |
| **A.8.29** | Security testing in development and acceptance | SAST/DAST/SCA integrated into CI/CD pipeline; penetration testing before major releases; security acceptance tests in test suites |
| **A.8.30** | Outsourced development | Third-party code security requirements in contracts; security review of externally developed components; SBOM for external code |
| **A.8.31** | Separation of development, test, and production environments | Strict environment segregation; no production credentials in development; no production data in staging |
| **A.8.32** | Change management | All changes through version-controlled process; security review as mandatory gate for significant changes |

## Access & Identity Controls

| Control | Name | Code-Level Check |
|---------|------|-----------------|
| **A.8.2** | Privileged access rights | Application enforces privilege separation; privileged operations require separate elevated tokens; all privileged actions audited |
| **A.8.3** | Information access restriction | RBAC/ABAC enforced at every API layer; deny-by-default access model |
| **A.8.4** | Access to source code | Source code access restricted to authorized developers; branch protection rules in place; signed commits |
| **A.8.5** | Secure authentication | MFA for all privileged access; strong password policies in code; OAuth 2.0/OIDC for federated auth |

---

## Data Protection Controls

| Control | Name | Code-Level Check |
|---------|------|-----------------|
| **A.8.11** | Data masking | PII masked in logs and non-production environments; field-level encryption for sensitive attributes |
| **A.8.12** | Data leakage prevention | Sensitive data not in error messages, logs, or API responses beyond what is needed |
| **A.8.24** | Use of cryptography | Only approved algorithms: AES-256, RSA-2048+, SHA-256+; no MD5, SHA1, DES; cryptographic choices documented |

---

## Monitoring & Vulnerability Controls

| Control | Name | Code-Level Check |
|---------|------|-----------------|
| **A.8.7** | Protection against malware | Input sanitization; file upload scanning; SCA to prevent malicious packages |
| **A.8.8** | Management of technical vulnerabilities | Regular vulnerability scanning; CVE-tracked remediation SLAs; SBOM maintained |
| **A.8.16** | Monitoring activities | Application-layer monitoring for security events; anomaly detection on API patterns; SIEM integration capability |

---

## Network & Infrastructure Controls

| Control | Name | Code-Level Check |
|---------|------|-----------------|
| **A.8.20** | Network security | Enforce TLS; validate certificates; implement certificate pinning where appropriate |
| **A.8.22** | Segregation of networks | Application does not trust network perimeter; zero-trust principles: verify every request |
